## Description

Retry of TODO-0025's Muon-vs-AdamW comparison (which was cancelled mid-run
because the double-conv architecture used there was too slow), this time on
LeNet -- user's own assessment that "LeNet is good for MNIST" prompted
trying `Muon` on the much cheaper LeNet-shaped architecture instead of
enhancing it further.

## Requirement

- New `BasicML/examples/train_lenet_mnist.py`: same LeNet shape as
  `demo/plot_dynamic_lenet_feature_maps.py` (6/16 conv channels, 120/84 FC),
  but with a genuine train/test split (15000/2500, matching TODO-0023's
  scale) instead of that demo's train-accuracy-only reporting.
- Same AdamW-vs-Muon comparison methodology as TODO-0025: `Muon` applied
  only to `Conv2D.w`/`Linear.w`, biases on a separate `AdamW`; both runs
  from identical initial weights, on the same split.
- Confirm actual runtime via smoke test before committing to a full run
  (given TODO-0025's estimate was wrong) -- measured ~6 min (AdamW) / ~18
  min (Muon, slower per-step due to Newton-Schulz iteration) for the full
  15000/15-epoch configuration; both launched as parallel background tasks.

## Outcome

Both runs completed. **AdamW**: stable, best test accuracy 98.40% (epoch
10), ends 98.20% (epoch 15) — confirms LeNet is genuinely well-suited to
MNIST at real held-out accuracy. **Muon+AdamW**: led early (95.60% after
epoch 1 vs. AdamW's 94.40%, best Muon epoch 96.80% at epoch 5) but diverged
from ~epoch 8 onward, ending at 73.00% test accuracy. Root cause is almost
certainly `MUON_LR=0.02` being carried over unchanged from a much smaller
MLP problem, with no LR decay — the classic signature of an LR too high for
this parameter scale, not evidence Muon is unsuited to CNNs. AdamW wins this
comparison as configured; a re-tuned Muon run (lower LR and/or a decay
schedule) was not attempted.
