## 2026-09-17 (P0 profiling)

**Machine state:** Not a fully idle machine — interactive desktop session with Firefox (several tabs) and other background processes running throughout. `/proc/loadavg` read 3.4–4.4 (1-min) across the session on an 8-core (`nproc`=8) box. Noted as a caveat on every number below; a genuinely idle box would likely show less run-to-run variance, especially at `OMP_NUM_THREADS=8`.

**Build:** `AdvanceML/build`, `CMAKE_BUILD_TYPE=Release` (CMakeLists.txt default), `-march=native` (`ADVANCEML_NATIVE_ARCH=ON`), oneDNN v3.9.1, `runtime:OpenMP` (GNU libgomp), `isa:Intel AVX-512 with Intel DL Boost`, `nthr:8` by default (matches `nproc`).

**Method:** `train_cnn_mnist` hardcodes `kEpochs = 10` with no CLI override, so profiling used `timeout <N>s` to cut the process off after roughly one epoch (~2-3s per epoch at this batch size) rather than editing the example to take an epoch-count argument (out of scope for this TODO). Two runs: (1) `ONEDNN_VERBOSE=1` captured to a log and aggregated per-primitive-kind by the verbose CSV's own reported per-call time; (2) `perf record -g` over the same kind of window, read with `perf report --stdio` and `--sort=dso`/`--sort=symbol`.

**oneDNN primitive time (ONEDNN_VERBOSE, ~1 epoch, 24.6k primitive-exec lines):**

| kind | total ms | count | avg ms |
|---|---|---|---|
| convolution | 3555.7 | 5021 | 0.708 |
| eltwise (relu) | 2739.8 | 3841 | 0.713 |
| batch_normalization | 2712.0 | 3841 | 0.706 |
| pooling | 1493.0 | 3841 | 0.389 |
| reorder | 438.7 | 6202 | 0.071 |
| matmul | 98.1 | 1870 | 0.052 |

Conv is the single largest kind (32%), but eltwise+batch_norm+pooling combined (63%) exceed it — P0's premise that "conv kernels may now dominate" does not hold on this build; BN/ReLU/pool together cost about twice what conv does. `reorder` (P1's target) is 4% of oneDNN time; `matmul` (dense layers) under 1%.

**`perf report --sort=dso` (self %, ~1 epoch window):**

| DSO | self % |
|---|---|
| `[JIT]` (oneDNN's own generated AVX-512 kernels) | 57.8 |
| `libgomp.so.1.0.0` | 39.5 |
| `libdnnl.so.3.9` (non-JIT, i.e. dispatch/setup) | 2.1 |
| `train_cnn_mnist` (our own code: autograd, `intern()`, arg-map building, layer `forward`/`backward`) | 0.18 |
| everything else (libc, libstdc++, ld.so) | <0.3 combined |

**Key finding:** our own framework code — the thing P1 (`intern()` linear scan) and P2 (per-op `unordered_map<int, memory>` arg construction, loss-loop `data()` hoisting) target — is 0.18% self-time of the whole profile. That is far below the noise floor set by machine non-idleness. The two real costs are (a) the JIT-compiled oneDNN kernels themselves (58%, expected and not something a "from-scratch, not reinventing BLAS" project should try to beat), and (b) `libgomp` overhead (39.5% self) — OpenMP fork/join and spin-wait across the ~16.5k primitive calls in one epoch (every primitive opens its own parallel region).

**Threading experiment (P0's "check threading settings"):** swept `OMP_NUM_THREADS` and read the epoch-1 time the binary itself prints, back to back, same machine state:

| `OMP_NUM_THREADS` | epoch 1 time |
|---|---|
| 2 | 1.85s |
| 4 | 1.50s |
| 6 | 1.89s |
| 7 | 1.88s |
| 8 (default = `nproc`) | 2.94s (one earlier run under identical env timed out past 20s — outlier, likely a contention spike; excluded but noted) |

Defaulting oneDNN/OpenMP to `nthr = nproc` on this interactive box is measurably worse than leaving headroom (`OMP_NUM_THREADS=4` fastest, ~2x default). This matches the `libgomp` self-time finding: with 8 requested threads directly matching 8 logical CPUs and background load (Firefox etc.) also wanting cycles, worker threads spin-wait for a scheduler slot instead of running, and that spin shows up as `libgomp` self-time. This is a real, reproducible-on-this-box effect, not just a one-off; the exact optimal thread count is machine-load-dependent so no single number is "correct" to hardcode, but defaulting to `nproc` unconditionally is the wrong assumption for a shared/interactive machine.

**Ordering decision for P1–P4, per the Requirement's "measured-cost order, reject what the profile shows isn't worth it":**

- **P1 (hashed layout registry):** profiled cost of `intern()`/registry search is invisible (bundled in the 0.18% "our own code" bucket) for this fixed-shape MNIST CNN — the existing linear scan's own comment is right that "a training run only ever sees a few dozen distinct descriptors" for this workload. Implementing anyway: it's a real algorithmic-complexity bug (O(n) per lookup, unbounded growth) that will matter for the variable-shape workloads (sequence lengths, batch sizes) the TODO calls out, it's a contained and low-risk change (swap a linear scan for a hash map, same pointer-stability guarantees since `unordered_map` values keep stable node addresses), and the TODO already specs a concrete test for it. Doing it now while it's cheap beats waiting for it to become an actual bottleneck. **Status: doing.**
- **P2 (per-op arg-map/desc allocations, loss-loop `data()` hoist):** the target code (all of `ops.cpp`, i.e. `train_cnn_mnist`'s DSO self-time) is 0.18%. Revisit if a future profile on a different workload (smaller batch, more primitive calls per sample) shows framework overhead actually growing past the noise floor.

## 2026-09-17 (implementation)

Branched `feature/TODO-0047-onednn-profiling-perf` off `dev`. All measurements below use `OMP_NUM_THREADS=4` (the P0 threading finding) for consistency; machine still not fully idle (see P0 caveat).

**P1 — hashed layout registry.** `AdvanceML/src/detail/dnnl_layout.cpp`: replaced the linear-scan `std::vector<shared_ptr<const Layout>>` with `std::unordered_map<dnnl::memory::desc, shared_ptr<const Layout>, DescHash, DescEqual>`. `DescHash` hashes `(data_type, dims, strides, inner_blks, inner_idxs)`; `DescEqual` falls back to `memory::desc::operator==` so a hash collision (or a field the hash misses) only costs an extra bucket compare, never a correctness bug. `unordered_map` keeps stable value addresses across inserts/rehashes (only erase invalidates), so `intern()`'s returned reference and every `Layout*` derived from it (`layout_id`, used as a pointer-identity cache key elsewhere) stays valid for the process lifetime, same guarantee the old vector had. New test `AdvanceML/tests/dnnl_layout_test.cpp`: interns 1,000 additional distinct descriptors around a 20-descriptor probe set and asserts repeated lookups of the probe set don't get more than 8x slower afterward (generous headroom over noise; actual result was 0.065µs vs a 1.49µs threshold — effectively flat).

**P2 — rejected**, per the P0 write-up above (our own framework code is 0.18% of profiled self-time). No code change.

**P3 — malloc retention, `mallopt`.** Added `advanceml::detail::tune_malloc_once()` in `AdvanceML/include/advanceml/buffer.hpp`, called from `AlignedDefaultInitAllocator::allocate()` (lazy, once per process via a function-local static). Initially implemented as the TODO's own hinted `mallopt(M_MMAP_THRESHOLD, 128 * 1024)` (128 KiB, glibc's un-tuned starting point) and found a *severe regression the TODO's data didn't surface*: 10-epoch wall time went from 16.05s to 25.95s (+62%) for a peak-RSS drop from ~205MB to ~148MB. Root cause: this workload's hottest repeated allocation (the conv1 activation/gradient, `mb128 x 16ch x 28 x 28 x f32` ~= 6.1 MiB) is freed and reallocated every forward/backward call; a threshold below that size forces every one of those through `mmap`/`munmap` (with a fresh page-fault cost on each), which costs far more than the RSS it saves. Swept the threshold (128KiB/1/2/4/6/8 MiB) back to back:

| `M_MMAP_THRESHOLD` | 10-epoch wall time | peak RSS |
|---|---|---|
| untuned (dynamic default) | 16.05s | ~205MB |
| 128 KiB | 25.95s | ~148MB |
| 2 MiB | 24.65s | ~137MB |
| 4 MiB | 22.37s | ~158MB |
| 6 MiB | 22.55s | ~158MB |
| **8 MiB (chosen)** | **16.56s / 16.61s (reran twice)** | **~185-187MB** |

8 MiB sits above the ~6.1MB hot buffer, so it never gets pushed through `mmap` — training speed matches the untuned baseline exactly, while peak RSS still drops ~9% (205→~186MB), because *fixing* the threshold at any value (not the specific value) stops glibc's dynamic-threshold growth, which was the actual mechanism behind the TODO's "grows over a run" observation. The TODO's own 148MB number is real but was reached with a threshold too low for this workload's buffer sizes and traded away 62% of training speed to get there — not a trade this project should make by default. Documented the full reasoning as a doc comment on `tune_malloc_once()` so a future reader doesn't "fix" it back down to a naive small threshold. `M_MMAP_THRESHOLD` accepts `int`, so this is glibc/Linux-only, guarded by `#if defined(__linux__) && defined(__GLIBC__)` (matches the rest of the repo's Linux/g++ dev target — see CLAUDE.md).

**P3 — duplicate conv inputs: deferred**, as decided in the P0 write-up (needs its own autograd design pass).

**P4 — relu >6D fallback.** `AdvanceML/src/ops.cpp`: `relu()` now checks `x.shape().size() > 6` and dispatches to a new `relu_scalar()` (plain loop, same `should_record`/`record` autograd wiring as `sigmoid`/`leaky_relu`) instead of going through oneDNN (`plain_desc` throws past 6D). New test in `AdvanceML/tests/kernel_perf_test.cpp`: 7D tensor, checked forward values and numerically verified the backward gradient.
