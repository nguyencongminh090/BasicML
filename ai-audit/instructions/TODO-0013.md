## 2026-09-08 11:00 (session)

**Discussed:** User asked to add a BatchNorm layer. A no-arg stub already
existed at `basicml/nn/batchnorm.py`. Asked via AskUserQuestion on three
axes before implementing: (1) BN semantics, (2) constructor signature,
(3) scope beyond the layer.

**Decision:**
- Full PyTorch-`BatchNorm1d` semantics: learnable `gamma`/`beta` as
  `requires_grad` Tensors in `parameters()`; running mean/var buffers
  updated with `momentum` during `train()`; `eval()` normalizes with the
  running buffers. Backward accumulates `gamma.grad`/`beta.grad` with `+=`.
- Signature `BatchNorm(num_features, eps=1e-5, momentum=0.1, affine=True)`.
  Dropped the stub's redundant `train`/`eval`/`__call__` overrides (Module
  already provides them) and the unused `init` import.
- Running-variance buffer uses the unbiased estimate (`n/(n-1)` factor),
  matching PyTorch; batch normalization itself uses the biased variance.
- Scope: layer + gradient-check cases in `examples/check_gradients.py`, no
  new demo. `nn/__init__.py` is empty in this repo (examples import from
  submodules, e.g. `from basicml.nn.batchnorm import BatchNorm`), so there
  is nothing to add there — "export" is satisfied by the module path.
- README left unchanged: its component table was deliberately not kept
  exhaustive when the 12 activation layers landed (TODO-0008), so BN is
  handled the same way.

**Gradient-check gotcha (resolved):** the stacked case originally used
`Linear(...)` (with bias) directly before `BatchNorm`. A bias immediately
before BN has an *identically zero* gradient (BN re-centres its input), so
the finite-difference check divided round-off by the `1e-8` floor in
`relative_error` and reported a spurious ~1e-2 error. Fixed by making the
pre-BN `Linear` layers `bias=False` in that test case (also the correct way
to use Linear+BN), with a comment explaining why. BN's own `gamma`/`beta`
and upstream (`dx`) gradients were verified correct against numeric
Jacobians independently.
