**Discussed:** User asked how OpenCL/SYCL on Intel Iris Xe compares to the current CPU oneDNN kernel, and whether SYCL/GPU would speed up CNN training on the current small MNIST model. Conclusion: no, model too small, iGPU dispatch/copy overhead would dominate. User then reported `train_cnn_mnist` is very slow per epoch and asked whether AdvanceML uses/supports vectorization effectively. Read `AdvanceML/src/ops.cpp` in full: `conv2d`/`pool2d`/`matmul` do use oneDNN primitives (AVX-512 VNNI via `-march=native`, `ADVANCEML_NATIVE_ARCH` in `AdvanceML/CMakeLists.txt`), but `conv2d()`'s forward and `backward_fn` construct a brand-new `primitive_desc` (JIT kernel selection) on every call instead of caching one per shape, and every primitive execute is immediately followed by `cpu_stream().wait()`. With `kBatchSize=128` over MNIST across `kEpochs=10` and 3 conv layers, this is thousands of primitive rebuilds per epoch — identified as the likely dominant cost, not lack of vectorization. Also noted several elementwise ops (`relu`, `batch_norm2d/1d`, global pools, `dropout`, activations using `exp`/`tanh`/`erf`) are hand-written scalar loops outside oneDNN, with unconfirmed compiler auto-vectorization.
**Decision:** Open this TODO to track the fix rather than implementing inline, since it changes internal engine architecture (primitive caching strategy) — per repo policy, architecture-touching changes need to go through the TODO/branch workflow, not be applied ad hoc mid-conversation.
**Next step:** Design a primitive cache (keyed by op + exact tensor shapes, since MNIST's last batch isn't full-size) for `conv2d`/`pool2d`/`matmul` in `ops.cpp`, reduce `cpu_stream().wait()` calls where safe, benchmark before/after epoch time on `train_cnn_mnist.cpp`, and audit the scalar elementwise ops for actual auto-vectorization (e.g. via compiler `-fopt-info-vec` or disassembly) before deciding whether any should move to oneDNN `eltwise`/`batch_normalization` primitives.

## 2026-09-17 (session 2 — implementation)

Branched `fix/TODO-0043-onednn-primitive-cache` off `dev` (stashed unrelated TODO-0042 WIP first, per user's explicit go-ahead to switch branches this session). Implemented item 1 from the TODO — added shape-keyed `unordered_map` caches (`gemm_cache()`, `pool_cache()`, `conv_cache()`) in `AdvanceML/src/ops.cpp` so `matmul`, `pool2d` (max/avg fwd+bwd), and `conv2d` (fwd, `backward_data`, `backward_weights`) build each `dnnl::primitive_desc`/`dnnl::primitive` once per distinct shape instead of every call, keyed on the *actual* tensor dims (so MNIST's smaller last batch gets its own cache entry, not reused incorrectly against the full-size one).

**Measured — and the primitive-rebuild hypothesis was wrong.** A standalone oneDNN micro-benchmark (`pd_bench.cpp`, isolated from the rest of the app) comparing "rebuild `primitive_desc` every call" vs "build once, reuse" for the network's actual conv shapes showed **no meaningful speedup** (0.75x–1.04x, within noise) — primitive_desc construction was never the dominant cost. The caching change is still correct/good practice (kept), but it is not what makes epochs slow.

**Root cause, confirmed via `DNNL_VERBOSE=1`:** `conv2d()` built its `src`/`weights`/`dst` memory descriptors with fixed `format_tag::nchw`/`oihw`. Forcing a plain (non-blocked) layout makes oneDNN silently pick `jit_uni_ncsp_convolution:conv+ref:any` — an unoptimized reference-style fallback kernel — instead of its AVX-512-VNNI-optimized blocked-layout kernel (`jit:avx512_core`). Confirmed AVX-512 *is* available and used by `pool2d` (already selects `jit:avx512_core` with plain `nchw` — pooling doesn't need blocked layout to vectorize) and `matmul` (already selects `gemm:jit:f32` with plain `ab` format) — only `conv2d` was hitting the slow fallback. A second standalone benchmark comparing the two paths for the `conv2` shape (16→32 channels, 28×28, batch 128) measured **~8ms/iter with `format_tag::any` + reorder vs ~2100ms/iter with forced plain format — roughly 180x**, even under this session's heavy background CPU contention (see caveat below).

**Fix applied:** changed `conv2d`'s `src_md`/`weights_md`/`dst_md` to `format_tag::any` (bias stays `format_tag::x`, 1D doesn't benefit from blocking) so oneDNN picks its optimal internal layout for forward, `backward_data`, and `backward_weights` independently. Since the rest of the codebase (`Tensor`) only ever holds plain contiguous NCHW/OIHW `float` data, added explicit `dnnl::reorder` calls (`reorder_to`/`reorder_into` helpers) at the boundary of each conv2d call: reorder plain→optimal going in, optimal→plain coming out. Reorder primitives are *not* cached (only the conv primitives themselves are, via the existing `conv_cache()`); this was accepted as fine given reorder cost is small (single-digit ms) relative to the ~180x win, but is a cheap follow-up if it ever shows up in profiling.

**Requirement checklist:**
- ctest: 59/59 pass, including the CNN gradient-check tests, confirming `format_tag::any` + reorder didn't change numerics.
- Correctness of primitive caching across the varying last-batch shape: verified by construction (cache key includes actual `N`/dims, not an assumed constant).
- Measured epoch time on `train_cnn_mnist.cpp`: **caveat — this machine had load average 9–12 on 8 cores during this session** (multiple concurrent Claude Code sessions, browser, etc.), so full end-to-end epoch numbers taken here are not clean before/after evidence; the isolated oneDNN micro-benchmarks (immune to that noise, since they're relative A/B within the same run) are the reliable evidence for the ~180x kernel-selection win. A clean single-job epoch-time re-measurement on an otherwise idle machine is still owed before closing this TODO.
- Item 4 (scalar elementwise op vectorization audit) not yet done this session — deferred to a follow-up pass, now lower priority since the conv kernel fix is the dominant win.

**End-to-end confirmation:** despite the noisy-load caveat above, ran `train_cnn_mnist` for one epoch before and after the fix, both in this same session (so at least comparably noisy): **445.59s/epoch before → 58.23s/epoch after, ~7.6x**. Consistent in direction and rough magnitude with the isolated kernel benchmark (which measured ~180x on the raw conv execute alone, before end-to-end overhead like reorders, other layers, Python-loop-equivalent driver code, and system contention dilute it). Good enough to consider the dominant bottleneck fixed; a fully clean idle-machine re-measurement would tighten the number but isn't required to close this out.

## 2026-09-17 (session 3 — performance review, K2 folded in)

A code-only performance review of `AdvanceML/` produced two new TODOs: TODO-0044 (autograd engine) and TODO-0045 (kernels/ops). The review's **K2** finding belongs to this TODO's item 4 rather than a new TODO. Findings to consider when doing item 4:

- `batch_norm2d` forward makes 3 single-threaded passes and backward 4 (`ops.cpp` ~1223-1327), while oneDNN runs conv across all cores; on `128×16×28×28` that's ~1.6M elements per pass. `relu`, `softmax`, `dropout` and `AdamW::step` are single-threaded too.
- BN backward computes the same sums twice: `grad_beta[c]` equals `sum_dout` and `grad_gamma[c]` equals `sum_dout_xhat`, in separate passes (also in `batch_norm1d`). Merge them into one pass, and merge the forward mean/variance passes as well.
- Options: oneDNN `batch_normalization_forward/backward` + `eltwise_forward/backward` primitives (threaded, vectorized, and able to stay in blocked layout, see TODO-0045 K1), or `#pragma omp parallel for` over the channel loop.
- Vectorization of loops calling `sqrt`/`exp`/`erf` is likely blocked by GCC's default `-fmath-errno`; the `-fno-math-errno` flag change is tracked in TODO-0045 K6, but check with `-fopt-info-vec-missed` as part of this audit.
