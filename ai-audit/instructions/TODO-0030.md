# TODO-0030 — AdvanceML: C++ autograd engine (scaffold)

## 2026-09-12

User's CPU/BasicML can't run CNN/Transformer workloads efficiently (pure NumPy, no BLAS backend, manual backward). Decided to start a new sibling project `AdvanceML/` in modern C++ with a real autograd engine, rather than modify BasicML (which intentionally stays teaching-focused, manual-backward, per its own CLAUDE.md rules).

**PyTorch-comparison question answered for the user:** hand-written C/C++ is not expected to beat oneDNN/MKL's hand-tuned AVX-512 VNNI GEMM/conv kernels — that's hundreds of thousands of engineer-hours of per-microarchitecture tuning, not realistic for a from-scratch project. The realistic win is cutting Python/dispatcher overhead around the *same* kernels PyTorch itself calls into (PyTorch doesn't hand-roll its GEMMs either). So AdvanceML wraps oneDNN rather than reinventing kernels, and the autograd graph / training loop / memory layout is where the from-scratch work and potential speed advantage actually live.

**Decisions locked in with the user (via AskUserQuestion):**
- Language: Modern C++ (C++20/23).
- Kernel backend: Intel oneDNN specifically (targets AVX-512 VNNI on this CPU), wrapped behind an internal interface for future swappability.
- Build system: CMake + Ninja (both already installed).
- Relationship to BasicML: run alongside, not replace — BasicML's rules in CLAUDE.md are untouched.
- Test framework: Catch2, via CMake `FetchContent` (not installed as a system package).

**Machine facts checked this session:** CPU confirmed to have AVX-512 VNNI (`__AVX512VNNI__` defined by `g++ -march=native`). `cmake`, `g++ 15.2`, `ninja`, `pkg-config` all present. `libdnnl3.6` and `libopenblas0` runtime libs present, but their `-dev` packages (`libdnnl-dev`, `libopenblas-dev`) are **not** installed — needed before `find_package(dnnl)` will succeed; installing them is a system-level change requiring the user's confirmation before running `apt install`.
